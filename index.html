Problema & Solução
Problema 1 — retenção

Nada pode ser apagado

O histórico de documentos é o ativo de treinamento de IA da empresa. Apagar um arquivo antigo destruiria dado que já foi pago para coletar.

Problema 2 — custo

Tudo cresce junto

50 mil arquivos novos por mês, para sempre, numa camada de acesso rápido tornariam o armazenamento sozinho capaz de inviabilizar o negócio em poucos anos.

Retenção eterna. Custo sob controle. Acesso rápido quando o cliente precisa.

Solução

Uma arquitetura serverless que guarda tudo, mas rebaixa o custo de armazenamento sozinha, com o tempo.

∞retenção, zero exclusão
P10:30
Nossa resposta

Uma arquitetura 100% serverless: paga-se pelo uso, não pela capacidade ociosa.

Três serviços gerenciados da AWS, cada um resolvendo uma parte específica do problema, sem nenhum servidor para provisionar ou manter.

01/

Entrada

API Gateway recebe e autentica cada requisição do cliente.

02/

Mediação

Lambda decide o que cada usuário pode ver — e gera o acesso.

03/

Retenção

S3 guarda tudo para sempre, rebaixando custo automaticamente.

P21:45
Cada serviço, explicado

O que é. Pra que usamos. Por que escolhemos. E em vez de quê.

01/
Amazon Cognito
"o segurança que confere identidade antes de tudo"
O que é
Serviço de identidade gerenciado — cadastro, login e emissão de token prontos.
Pra que usamos
Autenticar cada usuário e emitir o JWT do qual o restante do fluxo depende.
Por que
Elimina programar hash de senha, expiração de token e recuperação de conta na mão.
Em vez de
Landing page + banco de dados próprio — funcionaria, mas significa reimplementar (e arriscar) autenticação do zero.
02/
API Gateway
"a recepção que confere sua identidade"
O que é
Porta de entrada HTTP gerenciada, com autenticação embutida.
Pra que usamos
Validar a identidade do usuário antes de qualquer acesso a arquivo.
Por que
Elimina a necessidade de reimplementar autenticação em cada endpoint.
Em vez de
ALB + Lambda direto, ou Function URLs — perderíamos usage plans, API keys por cliente e o Authorizer nativo via JWT.
03/
AWS Lambda
"o atendente que busca só o seu documento"
O que é
Computação sob demanda, sem servidor para provisionar.
Pra que usamos
Gerar URLs assinadas restritas ao prefixo do usuário autenticado.
Por que
Cobrança só por invocação real — ideal para tráfego irregular.
Em vez de
EC2 ou ECS/Fargate — cobrariam capacidade ociosa entre uploads, indo contra o custo proporcional ao uso.
04/
Amazon S3
"o arquivo onde tudo fica guardado"
O que é
Armazenamento de objetos com 8 classes de custo diferentes.
Pra que usamos
Guardar todo o histórico, com prefixo por usuário e Lifecycle.
Por que
Único serviço que combina durabilidade de 11 noves com custo residual.
Em vez de
EFS ou um blob column em banco de dados — nenhum dos dois tem Lifecycle nativo para arquivamento frio automático.
P21:30
Decisões pensadas, não copiadas

Por que cada serviço venceu (e não a alternativa óbvia)

Em resumo: para cada peça da arquitetura, perguntamos "existe outro jeito de fazer isso, e por que não escolhemos ele?". O critério nunca foi "o que sabemos usar", foi "o que o requisito de negócio exige".

Serviço escolhidoAlternativa consideradaCritério decisivo
Amazon Cognito Autenticação própria (banco de dados + hash de senha + JWT assinado à mão) Zero código de autenticação pra manter — cadastro, login e emissão de token prontos, com 10.000 usuários ativos/mês grátis, indefinidamente.
API Gateway ALB + Lambda direto / Function URLs Precisávamos de usage plans e API keys por cliente, throttling nativo e integração pronta com Authorizer via JWT — sem escrever isso à mão.
AWS Lambda EC2 ou ECS/Fargate O tráfego de upload é imprevisível e em rajadas. Servidor fixo pagaria capacidade ociosa entre picos — Lambda cobra só a invocação real.
Amazon S3 EFS ou blob em banco de dados Só o S3 tem Lifecycle nativo para rebaixar classe de armazenamento automaticamente — sem isso, o requisito "nunca deletar" ficaria caro demais.

Deletar após X anos?

Descartado: violaria o requisito mais importante — o histórico é o ativo de treinamento futuro dos modelos de IA.

ACL pública por link direto?

Descartado: exporia arquivos de um cliente a outro. URL assinada resolve sem abrir mão de performance.

P21:30
Segurança & isolamento multi-tenant

Cinco camadas independentes, e nenhuma depende de boa vontade

01
Autenticação via Cognito — "ninguém entra sem crachá"
Todo acesso começa com login no Cognito. Sem um token JWT válido, emitido por ele, a requisição nem chega a ser avaliada pelas camadas abaixo.
02
Block Public Access — "um cofre sem vitrine"
Habilitado em 100% do bucket. Mesmo um erro futuro de configuração não consegue expor um objeto publicamente.
03
IAM de menor privilégio — "um crachá que só abre uma porta"
A role de execução da Lambda só tem s3:GetObject/PutObject dentro do prefixo do próprio usuário — mesmo um bug no código não vazaria dado de outro cliente, porque a permissão nem existe.
04
Prefixo por usuário — "uma gaveta com o nome de cada um"
Todo arquivo vive em usuario-{id}/arquivo.pdf — o ID do usuário autenticado vira a fronteira lógica que a política do IAM acima referencia diretamente.
05
URL assinada de curta duração — "uma chave que se autodestrói"
Nenhum cliente acessa o S3 diretamente. Toda leitura/escrita passa por uma presigned URL gerada pela Lambda, expirando em minutos.
P30:45
Além do dia 1

E se a DocMind IA crescer 10x amanhã?

📈 Escalabilidade — "cozinhas extras que abrem sozinhas quando lota"

API Gateway e Lambda escalam automaticamente por requisição — sem fila de espera, sem servidor para redimensionar. S3 não tem limite prático de objetos armazenados.

🛡️ Resiliência — "cópias em prédios diferentes, sem pedir"

S3 replica cada objeto entre múltiplas zonas de disponibilidade automaticamente (11 noves de durabilidade). Se uma zona falhar, o cliente nem percebe — não é um plano de contingência à parte, é o funcionamento padrão do serviço.

Em resumo: crescer não exige replanejar a arquitetura, e uma falha isolada da AWS não é motivo de pânico — o serviço já foi desenhado, por padrão, pra absorver os dois casos.

É a arquitetura que sustenta o resto da apresentação — os cenários "Enxuta" e "Escala" são variações dela, não pontos de partida diferentes.

Escala 10x + Enterprise
≈ $3.050/mês
500 mil arq./mês · 3 anos
  • + WAF, CloudFront e réplica cross-region
  • + Provisioned Concurrency (zero cold-start)
  • Custo cresce ~100x — a réplica cross-region sozinha dobra o armazenamento

O salto de custo na Escala não vem do volume de arquivos em si — vem de decisões de redundância (réplica em outra região) que qualquer arquitetura pagaria para ter o mesmo nível de proteção.

Premissas: região us-east-1, arquivo médio de 2 MB (5x maior no cenário de escala), sem custo de transferência de dados, preços oficiais AWS de jul/2026. No cenário de Escala, o total inclui réplica cross-region (dobra o armazenamento), WAF (Web ACL + regras + requisições) e Provisioned Concurrency estimados. Valores educacionais — não substituem a AWS Pricing Calculator para uma proposta comercial real.

Arquitetura pensada para crescer

Melhorias futuras: o que entraria na próxima fase

Não implementamos por escopo do case, mas sabemos exatamente onde cada peça se encaixaria.

01/

Amazon DynamoDB

Metadados do documento — nome, data, tamanho, status — sem depender só de ListObjects no S3 para consultas.

02/

AWS WAF

Camada de defesa na frente do API Gateway — bloqueia SQL injection, XSS e bots automatizados antes de chegar à Lambda.

03/

AWS KMS (SSE-KMS)

Chaves de criptografia gerenciadas e auditáveis para os objetos do S3 — rotação automática e rastro de auditoria de cada uso.

04/

EventBridge / Notificações do S3

Dispara automaticamente o pipeline de IA assim que um novo documento chega — arquitetura orientada a eventos, sem polling.

05/

Amazon CloudWatch

Logs, métricas e alarmes — visibilidade sobre erro e custo sem precisar caçar problema no escuro.

EXTRAreserva p/ perguntas
Antecipando a banca

Perguntas que vocês provavelmente vão nos fazer

Não é slide de discurso — é cola. Se a pergunta vier, a resposta já está pronta aqui.

"E a LGPD? O cliente pode pedir para apagar os dados dele?"

Sim — "nunca deletar" é a regra para o ativo de treinamento, não uma barreira legal. Na prática, um pedido de exclusão viraria um sinalizador de anonimização no metadado do documento (ver slide "Melhorias Futuras" — DynamoDB), não uma promessa quebrada.

"E se a AWS cair, vocês perdem tudo?"

Não. O S3 replica cada objeto automaticamente entre múltiplas zonas de disponibilidade — isso não é uma configuração extra, é o funcionamento padrão do serviço, com 11 noves de durabilidade.

"Por que não usar um servidor comum, tipo uma VM?"

Um servidor fixo cobra 24h por dia, mesmo às 3h da manhã sem nenhum upload. Serverless cobra só quando alguém realmente usa — essencial num negócio que ainda não sabe seu volume exato de crescimento.

"O Free Tier da AWS não acaba?"

Ele renova todo mês, não é um bônus único. No volume atual (~150 mil requisições/mês), a arquitetura fica dentro dele indefinidamente — só passa a pagar de verdade se o volume crescer bem além disso.

"Como vocês têm certeza que um cliente não vê o arquivo do outro?"

Não é promessa, é demonstrável: temos um simulador funcional que tenta o acesso indevido ao vivo e mostra o 403 sendo devolvido, camada por camada. Podemos rodar agora, se quiserem ver.

"Isso é só teoria ou dá pra montar de verdade?"

O CloudFormation do projeto cria bucket, política de Lifecycle e IAM automaticamente — é código, não slide. Qualquer pessoa da equipe consegue subir o ambiente do zero em poucos minutos.
